Best practice, rancangan fitur, penanganan issue tak terduga, dan analisa kondisi aplikasi salimapotek saat ini.

Dokumen Analisa — 14 Agustus 2026

1. Best Practice Manage Stock

Prinsip nomor satu di farmasi: stok tidak pernah “langsung diedit” — semua perubahan stok harus lewat transaksi yang tercatat (disebut stock ledger / stock movement). Ini yang membuat data bisa diaudit dan dilacak balik.

Model data inti

TabelIsi / Fungsi
obatMaster obat: kode unik, nama, golongan, satuan, min/max stok
batchSatu batch/lot: batch_no, expired_date, harga_beli, qty
stock_movementJurnal semua pergerakan: in/out, qty, ref (ke pembelian/dispensing), saldo_akhir
pembelian + detail_pembelianPenerimaan obat (stok masuk ke batch)

Aturan penting

🍃 FEFO (First Expired First Out)

Keluarkan batch dengan tanggal expired paling dekat saat dispensing. Wajib untuk farmasi — beda dengan toko biasa yang pakai FIFO.

⚖️ Satuan terkecil

Simpan semua qty dalam satuan dasar (misal tablet) + tabel konversi. Hindari error desimal & stok selalu selisih.

🏷️ Harga per batch

Simpan harga_beli di tabel batch supaya margin & COGS akurat saat harga antar batch berbeda.

📉 Min-max & reorder point

Tetapkan batas stok per obat, hitung otomatis kapan harus beli ulang.

Mandatory: batch_no & expired_date diwajibkan saat penerimaan — ini kunci pelacakan jika ada recall / pengembalian obat.

2. Fitur yang Dibuat di Aplikasi

Master Data

  • Obat: kode barcode, nama, golongan (bebas / bebas terbatas / keras / psikotropika / narkotika)
  • Kategori, satuan + konversi, pabrikan, supplier, rak / lokasi

Transaksi Utama

  • Pembelian: PO → penerimaan (input batch + expired) → retur beli
  • Pengobatan / dispensing: entry resep, otomatis kurangi stok via FEFO
  • Retur pasien: obat dikembalikan → stok masuk kembali

Kontrol Stok

  • Stock opname: hitung fisik, hitung selisih, lalu approve adjustment
  • Adjustment: susut, rusak, hilang, expired — wajib ada alasan + approval
  • Transfer antar rak / depo (jika ada lebih dari satu lokasi)

Monitoring & Peringatan

  • Peringatan stok di bawah reorder point
  • Daftar hampir expired (< 3 bulan) & expired — bisa auto-blokir jangan dijual
  • Fast moving / slow moving / dead stock (stok menumpuk)

Laporan

  • Kartu stok (riwayat lengkap per obat)
  • Laporan pembelian, penjualan, laba/rugi per obat
  • Laporan expired, laporan stock opname, laporan mutasi

Fitur Penunjang

  • Role & permission (apoteker vs admin vs kasir)
  • Audit trail — siapa mengubah apa kapan
  • Notifikasi (dashboard / WhatsApp / email), export Excel

3. Pertimbangan Issue Tak Terduga

🔻 Stok minus / selisih

Cegah stok negatif di level database, tapi sediakan jalur forced adjustment resmi dengan alasan + approval apoteker.

✏️ Salah entry (human error)

Jangan edit qty langsung. Pakai mekanisme void / koreksi: batalkan transaksi lama (tandai void=1, stok kembali otomatis) lalu entry ulang.

⚠️ Expired massal

Fitur write-off massal + laporan nilai kerugian. Ini juga alasan kenapa FEFO penting.

🏷️ Harga antar batch beda

Ambil harga jual dari batch yang dipilih (FEFO), bukan harga rata-rata, agar margin & laba akurat.

🖥️ Multi-kasir (concurrency)

Gunakan transaksi DB (BEGIN … COMMIT) + lock baris saat kurangi stok untuk mencegah overselling.

🔌 Sistem down

Form kertas sementara + fitur back-entry (tanggal mundur) agar data bisa diinput setelah sistem pulih.

💾 Backup

Backup database harian otomatis + prosedur restore. Ini penyelamat utama jika data korup.

🔁 Obat duplikat

Gunakan kode unik (EAN/barcode) sebagai kunci, bukan nama. Sediakan fitur merge obat.

4. Analisa Kondisi Aplikasi salimapotek Saat Ini

Kesimpulan utama: aplikasi saat ini bukan (belum) sistem stok/inventory — ini adalah sistem klinik/EHR + pencatatan resep (dispensing). Alur: pasien → visit → medical record → diagnosa → dokter menulis obat (trans_obat) → apotek melihat resep (Pharmacy) → laporan konsumsi (Reportobat, Monthlyobat).

Yang sudah bagus (fondasi)

  • Pola CRUD + DataTables server-side sudah rapi & konsisten (M_obat, M_reportobat, dll).
  • trans_obat sudah berisi data dispensing lengkap (obat, qty, harga, pasien, tanggal) — tinggal dijadikan sumber “stok keluar”.
  • Link medical_record → visit → patient sudah terbentuk.
  • Auth + role (check_akses) sudah ada — siap untuk pembagian peran apoteker/admin.
  • Kolom audit (insert_by, insert_dt) sudah dipakai di trans_obat.
